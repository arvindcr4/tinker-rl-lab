# Appendix D. Campaign Lane Detail

This appendix holds the lane-by-lane record behind Chapter 8: provenance of the training run, per-lane serving and scoping notes, the engineering history behind individual figures, the per-lane narratives of the six replacement scopes completed on 27 September 2026, the full E4 rerun audit, and the per-lane caveats of the small-scale reruns. None of it changes a figure reported in Chapter 8; every number here is quoted exactly as its source receipt records it, and the two reporting rules of Chapter 8 (no pooling of original-contract and replacement-scope results, no precision beyond the receipt) apply throughout.

## D.1 Actor identity, inference conditions and scoping notes

The design consequence of evaluating one actor for seed variance is specific: every suite number reported in Chapter 8 comes from one actor, and where a lane sampled more than one completion per task it did so to satisfy the suite's own protocol, not to estimate variance.

Inference conditions were frozen per lane and recorded in that lane's own receipt rather than imposed globally, and the lanes differ widely. The E10 native run declared a temperature of 0, a 32,768-token context, 4,096 output tokens per request, 3,600 seconds of wall time and an \$8 envelope. Its receipt also declares `max_generation_requests` = 1,967, which is a ceiling on generation requests, not a task count: the lane has 97 episodes, and the run recorded 414 native requests (405 in the main run and 9 in the continuation). The collector is written explicitly not to admit shorter native conditions (sources: `outputs/public_portfolio_2026-09-05/agentdojo_native_receipt.json`, `outputs/public_portfolio_2026-09-05/agentdojo_terminal_readiness.md`). The E11 run was sampled at temperature 0.2, top-p 0.95, 1,024 maximum output tokens and seed 1816, one sample per problem across all 312 prompts (source: `outputs/modal_e1_e14/2026-08-16/e11_full_receipt.json`). The point of recording them per lane is that the sampling regime is part of the result, not a detail beneath it.

Two scoping notes complete the picture of what the actor has actually been measured on. The E1 original-contract evaluation was a one-checkpoint evaluation whose 731 generations were produced by a mixed backend within a single run --- 476 Tinker generations and 255 Modal vLLM generations --- and that backend mix is recorded in the original receipt (source: `outputs/e1_e14_results_2026-09-05/E1_E14_Results.md`). Separately, two small probes exist at other parameter settings but are not suite results and are not reported as such: a base-model smoke run of the E11 harness measured zero scored tasks, and a four-task pilot on the step-40 checkpoint (the last training step, saved separately from `stepfinal`) returned four passes out of four with zero extraction failures while carrying an unresolved outstanding blocker --- the decontamination receipt identifier for that pilot does not exist, and the split-manifest validator still fails on it (sources: `outputs/e11_verilog_eval/e11_smoke_receipt.json`, `outputs/e11_verilog_eval/e11_trained_step40_receipt.json`).

## D.2 Training-run provenance

The two local files are excluded from version control by `.gitignore`, so they exist on the project workstation but not in the public repository.

Four things cannot be recovered, and they are listed so that no reader fills them in:

- **The exact training code.** The run records git commit `8fdade2f` with uncommitted changes that were never saved. The `pavlov_portfolio` preset and its dataset builder do not exist at that commit; they first appear in commit `72b9336d3` on 2026-08-14. The reward and data-pool code in Table 8.1 is therefore taken from the current tree, whose dataset hash does not match the recorded `bd1f0db6…`. It is the best reconstruction, not proof. The loss function and training loop are identical at `8fdade2f`.
- **Which 80 training prompts were drawn.** The draw used `random.Random(809)` over the 512-row pool, but the pool construction that ran is the unrecoverable code above.
- **The Tinker sampler weights.** They were purged with the run; the four checkpoints survive only on Hugging Face.
- **Any held-out training-time evaluation.** None was run (`evaluate_heldout` false).

The run also departs from `zvf-program/flagship/PAVLOV_EXPERIMENT_PROTOCOL_2026-08-09.md`. The protocol plans a learning-rate search and a twelve-suite curriculum with 1,200/128 prompt and response tokens. This run used two suites, 40 steps, 1,536/384 tokens and a learning rate of 1 × 10⁻⁵, and the protocol does not mention it; only the budget matches.

## D.6 Replacement-scope lane narratives, 27 September 2026

Three things changed in how the lanes were executed, and each is recorded as a deviation in the lane's own result file. First, where a fail-closed controller blocked only on paperwork that the directive had superseded, the lane used a thin runner that calls the benchmark's native loop and native grader directly. Second, compute moved off AWS: E2, E6 and E9 ran on Google Cloud virtual machines, E1's grading ran in Modal sandboxes, and E13 ran locally. Third, every lane was served the same actor, `pavlov-public-portfolio-bf16` (the base model with the seed809 adapter merged, §8.1), through vLLM with the non-thinking chat template. No lane went through the Tinker bridge whose missing stop sequences produced the E4 zero (§8.1.2, §8.5), so that defect is not expected here, although the lanes' result files do not record their stop settings. The shared endpoint served at a 32,768-token context. E5 used a dedicated 65,536-token copy of the same weights because its banking prompts exceed 32k.

**E1 --- SWE-bench Multilingual.** This run covers the 16 wave-10 recovery tasks and the 174 tasks that the 12 September waves never reached, 190 tasks in all. The actor resolved one (`phpoffice__phpspreadsheet-3463`), which is 1/190 = 0.53 per cent. Only 57 of the 190 produced a patch that applied and could be graded: 120 failed at patch application or evaluation and 13 produced an empty patch. Over graded tasks alone the rate is 1/57 = 1.75 per cent ([0.3, 9.3]). Thirteen tasks produced no generation and were scored as failures: eight exceeded the 32,768-token serving context and five hit provider errors. **E2 --- CORE-Bench, hard difficulty.** The actor answered every question correctly on 27 of the 45 `codeocean_hard` capsules, a task accuracy of 0.600. At the question level it answered 53 of 79 correctly: 28 of 33 written questions and 25 of 46 vision questions. Thirty-two tasks ended with the agent calling `finish`, ten at the 150-turn cap and three at the 8,100-second time limit. ## D.7 E4 rerun: closure and full audit

The E4 lane closed `CLOSED_PARTIAL` on 19 September 2026: the pass3/pass16 archive is genuinely missing, only one of six artifacts verifies, and the 0.3115 recovery metric stands as receipt-only evidence because unlimited budget removes a spending cap but cannot reconstruct model outputs that no longer exist. The only funded path recorded at closure was a fresh full rerun whose grader-only lower bound was estimated at approximately \$59.45, which sits outside every envelope then authorised. That path was subsequently authorised separately and executed, and its result is reported as a diagnostic rather than as a score, because that is what its design makes it.

The rerun was configured on the base model with a zero-initialised LoRA snapshot --- the lane's record states this is equivalent to base sampling, with no training steps --- executed through the Modal bridge `/v1/responses` path at `--n-concurrent 2` under a cap of \$55.91445263. It completed 100 of 100 trials with one `NonZeroAgentExitCodeError`, and returned a mean reward of exactly 0.0, with all one hundred trials in the 0.0 bucket, over a runtime of 3 hours 29 minutes (source: `outputs/PES_Phase2_Review_2026-09-12/finish/Pending_Experiments.md`, which cites the receipt at `outputs/e4_banker_toolbench/official_repo_ff6db552/jobs/btb-banking-tasks-tinker-bridge/result.json`).

The value of this run lies entirely in the failure mechanism, which was audited across all one hundred trajectories. Agents terminate after 2 to 14 steps, with a median of about 6, and produce no `deliverables/` directory; the verifier consequently short-circuits to 0.0 on the message "No deliverables found". Twenty-seven or more of the trajectories end in role-token degeneration of the form `user user assistant ...` repetition. The record at the time read this as the base model being unable to sustain the opencode tool-use loop. A later check does not support that reading. The bridge's `/v1/responses` path passed no stop sequences and decoded with special tokens removed, so generation ran past the end-of-turn token into invented `user`, `tool_response` and `assistant` turns, which is exactly the role-token degeneration observed (source: `outputs/e1_e14_small_scale_2026-09-26/E4/BRIDGE_STOP_TOKEN_FINDING.md`). Two implications follow, and they cut in opposite directions. The positive implication is that the harness behaves correctly at the boundary --- it fails closed, produces a legible mechanism for every zero, and does not manufacture partial credit. The negative implication is that no full-suite BankerToolBench score exists for this actor family; the only other measurement is the six-task subset of Tables 8.A and 8.B. The same bridge served E2, E5, E7 and the E9 streaming arm, so Table 8.2 marks those lanes as exposed to the same defect. In particular, the rerun's 0.0 must not be set against the original single-task outcome as though the two were a controlled pairing: they are different configurations under different runtime conditions, and the campaign makes no comparison between them.

Spend on the rerun was \$15.07 charged against the \$55.91 cap, comprising 16.35 million prompt tokens and 2.18 million completion tokens.

## D.9 Small-scale reruns: detail and per-lane caveats

Each lane's items, raw outputs and grader logs are kept so that every figure in Tables 8.A and 8.B can be recomputed (source: `outputs/e1_e14_small_scale_2026-09-26/PROTOCOL.md`).

For E12 the 151 rubric items come from only six generated applications, so they are not independent. The cluster-level test is an exact sign-flip test over the six per-app pass-rate differences (−0.042, +0.030, 0.000, −0.160, 0.000, −0.042), and it gives p = 0.25. The E12 grader is an LLM judge that is the same `Qwen/Qwen3.6-35B-A3B` base model as the base arm, so self-preference could favour the base arm. Two judge versions disagree widely (0.536 against 0.808 on the Tinker base run; `E12/result.json`). The E12 rates and difference are therefore judge-dependent, and no independent judge was run. For E4, all six tasks score 0 in both arms except `btb-19b3361c`; a Wilson interval is not valid for a mean of fractional [0, 1] rewards, and a bootstrap over one nonzero difference in six is degenerate. For E13, in 22 of the 26 episodes the progression is identical in the two arms. No lane-level difference is interpreted as evidence that the adapter improves or degrades performance unless its test excludes zero, and none is extrapolated to the full suite.

The principal caveat for each lane, as recorded in its result file, is listed below; the full list is in each lane's `result.json`.

- **E1.** New base-model arm; not comparable to or poolable with the original 2/731 (Tinker sampler route for the seed809 adapter purged, weights preserved on the Hugging Face branch; temperature 0.2).
- **E2.** Substitute benchmark; never pool with or present as the FrontierSWE lane score (original: 1/17 tasks, replay 0.8628; the seed809 adapter's Tinker sampler route has since been purged, its weights are preserved on the Hugging Face branch).
