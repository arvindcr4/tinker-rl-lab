\section{Query API, Auditor Badge, and \texttt{stackdiff}}
\label{sec:p6-query}

The reference CLI (\texttt{registry/query.py}, standard library only) is a
specification by example: any conforming implementation must reproduce its
outputs on the shipped entries.

\subsection{Query API}
\label{sec:p6-query-api}
The query surface is deliberately small---four verbs over the entry
directory:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize, frame=single,
  caption={The reference CLI surface.}, label={lst:p6-cli}]
python3 registry/query.py list
python3 registry/query.py query --item reference_kl [--full]
python3 registry/query.py badge [entry_id]
python3 registry/query.py stackdiff <entry_a> <entry_b>
\end{lstlisting}

\texttt{query -{}-item} classifies every stack as \texttt{FULL},
\texttt{PARTIAL}, or \texttt{UNREPORTED} on one MIN-REPORT item, where the
classification counts non-null leaves; the null-vs-explicit-absence convention
of Section~\ref{sec:p6-schema} does the real work here. \texttt{list} and the
JSON records themselves are the escape hatch: the format is plain JSON, so
\texttt{jq}, pandas, or a five-line script can express any richer query.

\subsection{The MIN-REPORT Auditor Badge}
\label{sec:p6-badge}
The badge maps a stack record to $[0,100]$:
\begin{equation}
  \mathrm{badge}(s) \;=\;
  \Big\lfloor 100 \cdot \tfrac{1}{7}\textstyle\sum_{i=1}^{7}
  c_i(s) \Big\rceil,
  \qquad
  c_i(s) = \frac{\#\{\text{non-null leaves of item } i\}}
                {\#\{\text{leaves of item } i\}},
  \label{eq:p6-badge}
\end{equation}
i.e.\ the mean per-item reporting coverage. The leaf sets are fixed by
\texttt{schema.json} (explanatory \texttt{source}/\texttt{description} keys
excluded): $10, 3, 4, 2, 3, 2, 2$ leaves for items 1--7, with the two clip
bounds dropped from item~1 when \texttt{clipping\_applied} is \texttt{false}.
Two design decisions matter.
First, items are weighted equally: a stack cannot buy a high badge by
over-documenting its sampler while staying silent on its loss form. Second,
the badge is \emph{outcome-blind}: the \texttt{outcomes} block is excluded, so
a collapsed run and a converged run with equal reporting earn equal badges.
The badge answers ``can this stack be audited?''---never ``is this stack
good?''. \ifdefined\SUBMISSIONBUILD Current badge values are summarized in Table~\ref{tab:p6-entries-summary} (full per-entry listing in Table~\ref{tab:p6-entries}, Appendix~\ref{app:p6s-entries}; regenerated with \texttt{registry/query.py badge})\else Current badge values are listed in Table~\ref{tab:p6-entries}
(regenerated with \texttt{registry/query.py badge})\fi{}.

\subsection{\texttt{stackdiff} and the R0--R5 Severity Ladder}
\label{sec:p6-stackdiff}
\texttt{stackdiff} compares two stack records over a fixed catalogue of
\NFIELDS{} canonical fields (\texttt{FIELDS} in \texttt{registry/query.py}),
each with a fixed severity, plus the per-variant-delta status rows. Values come
from an entry's \texttt{run\_config} block when present---written by
\texttt{registry/generate\_entries.py} from the run sources, with per-field
provenance (\texttt{logged}, \texttt{code}, \texttt{default},
\texttt{inferred}, or \texttt{unknown}) and the source location of each
value---and otherwise from the hand-entered fields:
\begin{itemize}[leftmargin=1.5em, itemsep=0.1em]
  \item \textbf{R5} --- outcome-critical: execution mode, checkpoint id,
        base/instruct variant and revision, reward function id, prompt
        template hash and chat template, dataset, evaluation metric and
        held-out protocol.
  \item \textbf{R4} --- algorithm: objective, importance ratio, clipping,
        aggregation, advantage normalization, token mask, length
        normalization, dynamic sampling, reward shaping, inner epochs, KL
        reference/coefficient/estimator, and variant-delta status.
  \item \textbf{R3} --- hyperparameters and budget: decoding, batch shape,
        group schedule, steps, sampler refresh, data subset and selection,
        optimizer, LoRA.
  \item \textbf{R2} --- runtime: trainer, backend, precision, reward-function
        source hash.
  \item \textbf{R1} --- nuisance: trainer version, seeds.
\end{itemize}
The reported level is the maximum severity over fields that are \emph{known
on both sides and differ}; in particular, R5 is assigned only from a known,
differing outcome-critical field. Fields unknown on either side never raise
the level; a variant-delta row declared on only one side counts as unknown,
not absent. Unknowns are reported separately as a \emph{coverage} score (fraction
of compared fields known on both sides), a \emph{hidden severity} (the highest
rung that could still differ), and an \textsc{underspecified} flag (coverage
below $0.8$, or any R5 field other than the never-pinned checkpoint revision
unknown). Checkpoint and dataset identifiers are compared after normalization
(bracketed notes dropped, case ignored, \texttt{gsm8k} $\equiv$
\texttt{openai/gsm8k:main}). An earlier version of the tool did not compare
the model field and emitted R5 whenever a field was null; both behaviours are
fixed in the version described here.

\paragraph{Output on the shipped registry.}
\texttt{python3 registry/query.py stackdiff -{}-all} over the \NSTACK{} stack
records (\STACKDIFFNPAIRS{} pairs) reports \STACKDIFFDIST{};
\STACKDIFFUNDER{} pairs are underspecified (median coverage \COVMED{}). R5
dominates because the entries span six base models, which normalize to seven
checkpoint strings (the two Llama-3.1-8B-Instruct entries differ by an
organization prefix that the normalizer does not strip, so they do not
pair): checkpoint identity is
the differing R5 field in nearly every R5 pair. Holding the checkpoint fixed
shows that the ladder discriminates: the checkpoint-sharing pairs give \SAMECKPT{}. The R0 count needs
a caveat. R0 means no known difference, not verified equivalence, and all
\NRZERO{} R0 pairs are underspecified. Identical normalized signatures,
including their unknown states, form only one non-singleton class:
the OpenRLHF and veRL config records. R0 is not itself a transitive
equivalence relation when different pairs expose different known fields.
Collapsing that identical-signature class leaves \DEDUPN{}
entries and \DEDUPALL{}; among checkpoint-sharing pairs, \DEDUPSAME{}. The two
same-checkpoint R5 pairs are real runs versus dry runs (execution mode).
Restricted to the \NGEN{} generated entries, \GENPAIRS{}.

On the backend exhibit (\texttt{trl\_grpo\_qwen3-8b\_gsm8k} vs.\
\texttt{tinker\_grpo\_qwen3-8b\_gsm8k}) the tool reports R5 from checkpoint
(Instruct vs.\ Base), reward parser, prompt template, and chat template, plus
R4 (token mask), R3 (batch shape, sampler refresh, data subset and selection,
optimizer), and R2 (trainer, reward source) differences, at coverage
\STACKDIFFCOVA{}---the confounds the label hid. On the two ``DAPO'' entries it
reports R5 (model, task, reward, evaluation) and R4 differences including
dynamic sampling (resample-then-drop surrogate vs.\ absent), at coverage \STACKDIFFCOVB{}
(Section~\ref{sec:p6-worked-dapo}). The ladder is a \emph{risk} scale, not an
effect-size scale. When a same-label pair reaches R4 or above, the CLI prints a
warning that outcome differences must not be attributed to the shared label;
\texttt{-{}-exit-level} returns the level as the exit code for CI use (exit
code 6 marks an R0 with unresolved comparability).

\paragraph{Limitation: hand-entered entries cap coverage.} \NHAND{} of the
\NSTACK{} stack entries are still hand-entered (\texttt{generate\_entries.py}
has no adapter for their sources, including the N2 run script), so most of their fields are unknown; this is why median pair
coverage is \COVMED{} and why \STACKDIFFUNDER{} pairs are underspecified. The \NGEN{}
generated entries still require pair-specific coverage checks. No
trainer-side manifest emitter is shipped: entries are written by hand or
regenerated by \texttt{generate\_entries.py} from existing run scripts.
