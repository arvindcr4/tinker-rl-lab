# 5. Implementation Details

This chapter describes what was built. Its organising claim is that the engineering contribution of the project is a **dispatch and evidence layer** rather than a training algorithm: the algorithmic content of GRPO is inherited from the literature, but the work of making six reinforcement-learning frameworks and six compute backends addressable through one Tinker-style interface — and of recording the evidence needed to trace outputs to their configuration and artefacts, while marking incomplete historical bindings — is where the implementation effort sits. The chapter proceeds from the abstraction (the adapter architecture), through the concrete training loop, to the two engineering episodes that most shaped the codebase (the parallel logging defect and the Colab white-box path), and finally to the evaluation harness and the recovery re-implementations undertaken after an execution-source loss in the final phase of the project.

## 5.1 Two Rosters, One Dispatch Surface

A reader approaching the project's comparison material will encounter two different framework rosters, and conflating them is the single most likely misreading of the implementation. The internal reports' shared methods note states the distinction explicitly: the cross-launcher LLM-RL scaffold referenced in the framework-gap discussion is a seven-library roster — Tinker, TRL, SkyRL, veRL, OpenRLHF, Atropos, and HF reference launchers — that targets LLM post-training launchers specifically, while the cross-RL-library evidence reported elsewhere uses a different roster. Critically for this chapter, the same note records that "only Tinker and TRL produced completed runs in this release; veRL and OpenRLHF entries in the `framework_comparison.json` artefact are dry-run placeholders" (source: platform_hybrid/paper/sections/_shared_methods.tex). The veRL and OpenRLHF entries in that artefact carry peak and last-ten-average reward values, but they are the output of the harness resolving a launch plan, not the output of a training run, and they must never be pooled with real results or read as framework comparison evidence.

Atropos occupies a different position again. Rather than being a cell in the dispatch matrix, it is integrated through a dedicated package under `platform_tinker/atropos/`, a `tinker_atropos` module containing `config.py`, `api.py`, `trainer.py`, `types.py`, `dataset.py`, `stats_utils.py`, and an `environments/` directory with per-task environment servers (source: platform_tinker/atropos/). Its integration model is the Atropos managed-server pattern: a three-terminal workflow in which `run-api` starts the Atropos API, `launch_training.py --config configs/default.yaml` starts Tinker training against a `TINKER_API_KEY`, and an environment server — a built-in one or any external Atropos environment pointed at the same config file — serves rollouts. The README's quickstart example runs a fifty-step training run on Llama-3.1-8B-Instruct against a GSM8K environment, and the environment contract is that the `env` and `openai` sections are consumed by the environment server while the `tinker` section is consumed by the trainer and ignored by the environment (source: platform_tinker/atropos/README.md). This separation is what allows an arbitrary existing Atropos environment to be reused against the Tinker backend without modification to the environment.

## 5.2 The Adapter Architecture: What versus Where

The dispatch surface is built on one orthogonal decomposition, stated in the backends module docstring: "A `Backend` knows **where** to run one experiment cell (local GPU, Modal, Colab, vast.ai, GCP, HF Spaces); the framework dimension (trl/tinker/verl/openrlhf/skyrl) is the **what**. `plan()` resolves a cell into a concrete `LaunchPlan` without spending compute, so `--dry-run` and the matrix test work uniformly" (source: platform_local/unified/backends/base.py). The `LaunchPlan` dataclass carries `backend`, `framework`, `command`, `driver_file`, `output`, `env`, and `notes`, with a `format()` method for printing; the default `_execute` runs `subprocess.run(plan.command, shell=True, check=True)`. Because plan resolution is separated from execution, the entire matrix can be validated without a GPU, an API key, or a dollar of spend — a property that the dry-run placeholders discussed above depend on, and which is also the reason those placeholders must be labelled as such.

The matrix itself ships as data. `platform_local/unified/matrix.json` declares schema `tinkerrl-framework-backend-matrix-v1` with thirty cells — five frameworks (trl, tinker, verl, openrlhf, skyrl) crossed with six backends (local, modal, colab, vast, gcp, hfspaces), five framework cells per backend and six backend cells per framework — and a `canonical_experiment` block that pins the single configuration every cell is meant to instantiate: `Qwen/Qwen3-8B` on GSM8K with GRPO, thirty training steps, `num_generations` 8, per-device batch size 2, gradient accumulation 8, learning rate `1e-06`, LoRA rank 16 and alpha 32 over all linear modules, `beta` 0.0, `epsilon` 0.2, maximum completion length 1024, and seed 211 (source: platform_local/unified/matrix.json). Each cell is a concrete plan naming a framework, a backend, the launch command, the driver file and an output location; for example, the `trl`/`local` cell runs `python -m platform_local.unified --backend local --framework trl` and dispatches in-process to `platform_local/trl_integrations/trainer.py`.

The launcher implements the dispatch. `UnifiedLauncher` holds three registries: `FRAMEWORKS` mapping `skyrl`, `tinker`, `verl`, `openrlhf`, and `trl` to human-readable labels; `BACKENDS` mapping `local`, `modal`, `colab`, `vast`, `gcp`, and `hfspaces` to labels; and `ALGORITHMS` covering `grpo`, `ppo`, `reinforce`, `dapo`, and `dpo` (source: platform_local/unified/launcher.py). Dispatch is outer-on-backend and inner-on-framework, which is why the per-framework handlers can each be written against the framework's own idioms. `_run_tinker` shells to `python -m platform_tinker.tinkerrl.grpo_cli --preset <spec.task>`; `_run_openrlhf` delegates to `platform_modal/openrlhf/trainer.py:run_openrlhf_training({}, output_dir="./checkpoints/openrlhf")`, which drives `openrlhf.cli.train_ppo_ray --advantage_estimator group_norm`; `_run_trl` generates a resumable GRPO training script through `trl_integrations.trainer.generate_trl_train_script` into a temporary directory and executes it; `_run_verl` imports `verl.config` and `verl.trainer` directly; and `_run_skyrl` requires a `SKYRL_CHECKOUT` environment variable and emits `uv run --extra gpu --extra tinker -m skyrl.tinker.api` (source: platform_local/unified/launcher.py). For the `local` and `colab` backends the launcher runs `dispatch_framework()` in-process, a path the code comments identify as the one that breaks the Colab entry's self-recursion — an implementation detail worth recording because it indicates that the backend and framework dimensions are not perfectly orthogonal in practice, and the launcher carries framework-specific knowledge precisely at the points where they intersect.

Fairness across frameworks is addressed by configuration auditing rather than by assertion. The `platform_hybrid/experiments/framework_config_dumps/` supplement ships one proposed configuration template per framework for the intended Qwen3-8B + GSM8K comparison, and the accompanying README recomputes the field partition from those templates: of 44 tracked leaf fields, 25 are identical across all four frameworks (LoRA rank, alpha, target modules and dropout; GRPO group size, rollouts per group and max new tokens; sampling temperature, top-p, top-k and do-sample; optimizer name, learning rate, weight decay, betas and epsilon; reward type; the task, seed and source-git-sha metadata; four PPO settings; and bf16), while 11 are Tinker-managed — serialised as `null  # managed_by_tinker` in the Tinker dump — covering `kl.beta`, `kl.surrogate`, importance-sampling granularity, reference-model offload and recompute, tokens per optimizer step, reward broadcast precision, gradient checkpointing, micro-batch size, gradient accumulation, and tensor-parallel size (source: platform_hybrid/experiments/framework_config_dumps/README.md). The same README records two disclaimers that matter more than the identical count: `model` and `model_sha256` are *not* identical, because the Tinker template names `Qwen/Qwen3-8B-Base` while TRL, veRL and OpenRLHF use the instruction-tuned `Qwen/Qwen3-8B`, and `model_sha256` is a placeholder rather than a verified checksum. The partition is exhaustive, 25 + 11 + 8 = 44 (recomputed from the four YAMLs by `tools/review_ledger/Thesis_2026_10_11_ESA_Corrected_config_partition.py`). Within the 11 Tinker-managed fields the three open frameworks also differ among themselves: KL beta is 0.04 for TRL and veRL against 0.02 for OpenRLHF, and importance-sampling granularity is token-level for TRL and veRL against sequence-level for OpenRLHF. The remaining eight fields differ across the four templates and are documented rather than harmonised: `model` and `model_sha256` (above), framework name and version, reference-model placement (`on_device`, `managed`, `separate_process` and `sharded_ray`), GPU memory utilisation, inference backend and number of minibatches. The appendix's original "byte-identical" framing is retracted on the strength of this partition; the accurate statement is that a majority of template fields agree, without proving matched execution; the TRL code/dump rank conflict remains unresolved, a known Base-versus-Instruct confound survives, and eleven fields are not under user control at the Tinker API level at all.

## 5.3 The Custom-Loss Tinker Reference Loop

The reference implementation of the training loop lives in `platform_tinker/tinkerrl/grpo.py` and is exposed through `grpo_cli.py`. The loop follows the standard four-stage shape recorded in the Phase-1 report under "The Tinker GRPO Loop": sample a group of `G` completions per prompt, compute group-relative advantages, form the loss, and take an optimiser step (source: platform_tinker/reports/esa_phase1/Phase1_Project_Report_ZVF.tex). By default advantages are group z-scores, $A_i=(r_i-\mu_g)/(\sigma_g+10^{-8})$ with the population $\sigma_g$ (`normalize_rewards`); with `unbiased=True` they are the unscaled centred rewards $A_i=r_i-\mu_g$ (the Dr. GRPO standard-deviation fix). The loss is not the clipped, KL-regularised surrogate of the original GRPO paper. It is REINFORCE with a group-mean baseline (z-scored by default),

$$L(\theta) = -\frac{1}{N} \sum_{i=1}^{N} A_i \sum_{t=1}^{T_i} \log \pi_\theta(y_{i,t} \mid x, y_{i,<t}) \;+\; \lambda_{\mathrm{NLL}}\Bigl(-\frac{1}{|M|}\sum_{i\in M}\frac{1}{T_i}\sum_{t=1}^{T_i}\log \pi_\theta(y_{i,t}\mid x,y_{i,<t})\Bigr)$$

where $T_i$ is the passed response length, so only response tokens enter both sums, $M$ is the optional set of masked (correct) responses and $\lambda_{\mathrm{NLL}}$ the optional auxiliary coefficient (default 0, which removes the second term). The policy term is a token sum per response averaged over the $N$ completions, with no importance ratio, no clipping, no KL term and no reference policy (source: platform_tinker/tinkerrl/grpo.py, `make_grpo_loss_fn`). The inspected current source masks the loss to response tokens and refreshes the behaviour sampler every training step. Earlier candidate implementations used full-sequence scoring or checkpoint-only refresh, but their binding to the historical actor is unknown. The response-mask repair is dated 3 October 2026, after the campaign actor; it cannot retroactively certify that run. Optional GSPO and auxiliary paths in the current source are outside this default-path description. The implementation uses the Tinker SDK's `ServiceClient` with `create_lora_training_client`, `forward_backward_custom` with `loss_type_input="logprobs"` so that per-token log-probabilities flow into a custom loss, `optim_step` with `AdamParams`, and `sample()` for rollouts; resumption uses `create_training_client_from_state_with_optimizer` (source: platform_tinker/tinkerrl/grpo_cli.py).

This custom-loss implementation is distinct from `scripts/n2_reward_tensor_20260704.py` and `scripts/qp7_adaptive_g_20260704.py`, which pass sampler log-probabilities into the SDK `importance_sampling` loss and use mean-centred advantages without standard-deviation division. They have ratio terms but no configured clipping. Table 4.2 lists these as separate runner families. An SDK loss identifier establishes the requested interface, not independently verified server internals or a binding to the historical campaign actor. Conversely, the minimal PPO comparator has a sequence-level clipped ratio objective: missing GAE and critic warm-up make it a limited baseline, not an unclipped REINFORCE implementation.

The single most consequential property of this loop for the project's research questions is the degenerate case. When the group's reward standard deviation $\sigma_g$ is zero, every advantage $A_i$ is zero, and because the loss has no KL or auxiliary term, the group contributes exactly zero gradient. This is the mechanism behind the zero-variance-fraction diagnostic that runs through the project; it is recorded in the Phase-1 report as the observation that motivated the collapse analysis, and it is the reason `zero_loss` and `zero_reward` are first-class outputs of the training CLI rather than derived quantities. Zero reward is counted as an average reward equal to zero; the available implementation in `platform_tinker/tinkerrl/grpo.py` increments `zero_loss_steps` when `abs(loss_val) < 1e-6`, and the CLI prints that counter. The exact predicate/source binding of the historical actor receipt remains unverified; NFR-9 is Not Met for that historical actor, and its count is not a count of zero-gradient or zero-parameter-update steps (source: platform_tinker/tinkerrl/grpo_cli.py).

The CLI exposes eight presets — `tooluse_synth`, `tooluse_baseline`, `tooluse_heldout`, `tooluse_xlam`, `gsm8k`, `math100`, `pavlov_xlam`, and `pavlov_portfolio` — each resolving a dataset factory and a reward function through a `DATASET_FACTORIES` registry and a `REWARD_MAP` (`ExactMathReward` for GSM8K, `StrictToolCallReward` for `pavlov_xlam`, `PavlovNonXLAMReward` for `pavlov_portfolio`). Tracking and campaign gates are enforced before a run starts, through `config.validate_tracking()` and `config.validate_campaign_gate()`, and the CLI refuses to launch without a `TINKER_API_KEY`. Each seed's result is printed as a structured record containing `run_id`, `sampler`, `avg_first5`, `avg_last10`, `peak_reward`, `zero_loss`, `zero_reward`, `heldout_reward`, and `reward_trace`, so that a run's evidence is emitted at the point of execution rather than reconstructed afterwards. The eight presets replaced an earlier collection of standalone `grpo_*.py` scripts, with `legacy_main` retained to translate the old flag surface (source: platform_tinker/tinkerrl/grpo_cli.py).

## 5.4 The Parallel Runner and a Real Logging Defect

Sweep execution is handled by `parallel_sweep.py` and `campaign.py`, with the runner's design shaped directly by a defect found during development. The defect is documented in the group-size sweep findings and is worth quoting in full, because it is the clearest illustration in the project of why logging infrastructure deserves the same scrutiny as training code:

> The threaded runner trains all G in parallel correctly, BUT `wandb` uses a thread-unsafe global `run` — with 4 threads calling `wandb.init(reinit=True)`, the G8/G16 **summary** writes failed ("Run is finished") after another thread finished its run. Per-step `wandb.log` mostly survived; the summary dict didn't. **Fix for next parallel batch:** isolate each run in its own PROCESS (multiprocessing / subprocess per config), not a thread — or use `wandb-core` service mode with explicit per-run objects. Training itself was unaffected (all step data is in the run log).
> (source: platform_hybrid/experiments/results/p3_groupsize/FINDINGS.md)

Two aspects of this record are instructive. First, the failure was silent with respect to training: steps completed and per-step metrics were written; the logging diagnosis does not independently demonstrate gradient correctness. Only the run summary — the aggregated dictionary from which a results table would be built — was lost, which is precisely the class of failure that corrupts downstream reporting while leaving the primary artefact intact. Second, the remedy adopted was structural rather than retry-based: isolating each run in its own process removes the shared mutable global entirely, whereas retrying the summary write would have left the race in place. The finding also notes the alternative of `wandb-core` service mode with explicit per-run objects, which would preserve in-process execution at the cost of depending on service-mode semantics that the project chose not to rely on.

The same findings file documents the group-size sweep that exposed the defect, and its numbers are reported here with the qualifications the source attaches to them. The sweep ran `G ∈ {2, 4, 8, 16}` on Qwen3.5-4B for six steps on GSM8K at seed 0 under the W&B group `p3-groupsize-sweep`, with total token counts of 9,663, 19,964, 34,084, and 68,055 respectively. At `G = 2` the run showed a 50% batch-level collapse with a `+0.000` gain; at `G = 4` a 17% collapse with a `+0.125` gain. The source flags the `G = 4` gain explicitly as supported by one example at n = 8 on a single seed and therefore *suggestive rather than proven*, and records that the independent verification of the sweep returned the verdict SUSPECT (source: platform_hybrid/experiments/results/p3_groupsize/FINDINGS.md). These are not results this thesis claims; they are the observations that motivated the group-size investigation and that the later controlled work supersedes, and they are reported in the register in which they were recorded.

## 5.5 The Colab White-Box Path (Per-Layer Gradient Profile)

The per-layer gradient profile — numbered P1 in the Phase-1 series, and distinct from the P1 cross-scale study of Chapter 6 — asks a question the managed Tinker backend cannot answer. Per-layer gradient norms require access to the model's internals during the backward pass, and the managed service exposes no such interface. The implementation therefore leaves the managed path entirely and runs on a Colab L4 GPU in `platform_hybrid/experiments/openings/p1_layer_profile.py`, using Qwen2.5-1.5B-Instruct with LoRA adapters on the q/k/v/o projections, five GRPO-style advantage-weighted steps, and per-layer LoRA gradient norms recorded at each step (source: platform_hybrid/experiments/results/p1_layerfreeze/FINDINGS.md; platform_tinker/reports/esa_phase1/Phase1_Project_Report_ZVF.tex). The white-box path is thus a deliberate architectural exception: the project accepts the loss of managed-scale training in exchange for gradient visibility, and confines the exception to a question that only gradient visibility can address.

The first-pass result appeared strong. Across 28 layers, the top-k layer set identified at step 1 overlapped the final top-k set perfectly, with a measured overlap of 1.0; the top 25% of layers accounted for a 0.476 share of gradient mass; layer 0 carried a gradient norm of 63 against 6–17 elsewhere, and a secondary mid-late band appeared at layers 17–23. A scaled re-test disciplined this result. The re-run used `p1_layer_profile_scaled.py` on Qwen2.5-3B-Instruct, with 24 real GSM8K problems, ten steps, `G = 4`, 36 layers, and seeds {0, 1}. The stored step-1 overlap fell to 0.111, and the top-25% concentration measured 0.39 with a standard deviation of 0.013. The source's verdict is unambiguous: the original predictability finding "was an artifact of the toy 1.5B/hardcoded-arithmetic setup" (source: platform_hybrid/experiments/results/p1_layerfreeze/FINDINGS.md). A later four-seed pass at the same configuration (seeds {0, 1, 2, 3}) supersedes the two-seed figure and gives a mean overlap of 0.083 ± 0.048 (mean ± SD), with concentration 0.39 (source: platform_hybrid/experiments/results/p1_layerfreeze/scaled_4seed_result.json). The implementation compares the top nine of 36 layers at step 1 with the top nine by gradient norm summed over all ten steps, including step 1; it does not compare with an independent final-step target. For two independent uniformly selected nine-layer sets, expected intersection divided by nine is 9/36 = 0.25, so describing 0.111 or 0.083 as the chance expectation was incorrect. The observed overlap is below that simple reference, without establishing a general anticorrelation or a statistically calibrated null (source: platform_hybrid/experiments/openings/p1_layer_profile_scaled.py, lines 229–235).

A companion freeze test asked whether the layer profile could be exploited: if a small band of layers dominates the gradient, freezing the rest should preserve the benefit at lower cost. The small comparison did not establish performance preservation. The full 28-layer configuration trained 2.18M parameters and produced a mean held-out gain of `+0.0625` (seed 0 `+0.125`, seed 1 0.0). Freezing to a hot band comprising layer 0 plus layers 12–27 — 17 layers, 1.32M parameters, or 0.61 times the full count — produced `+0.000`. The source concludes that "aggressive freezing loses the benefit… The freeze lever does not work at this scale", and records that the comparison is underpowered at n = 8 held-out examples over 2 seeds (source: platform_hybrid/experiments/results/p1_layerfreeze/FREEZE_FINDINGS.md). The layer-ranking result did not replicate in the tested 3B configuration, which also changed task and recipe; scale is not isolated as the cause. The two-seed, eight-example freezing comparison is inconclusive about performance preservation or ineffectiveness. Both observations are retained with those limits.

## 5.6 Software Modules

The following inventory describes the RL-related modules relevant to this thesis. The unified launcher, `platform_local/unified/launcher.py`, maps one configuration onto a chosen backend; `platform_tinker/tinkerrl/grpo.py` is the group-standardised REINFORCE reference loop against the managed backend; `platform_local/trl_integrations/` and the `verl/` integration hold the per-framework adapters, with `platform_modal/openrlhf/` and `platform_hybrid/skyrl/` completing the roster, and `platform_tinker/atropos/` carrying the Atropos integration described above. Analysis code is separated from training code by intent: `p2_collapse_analysis.py` recomputes zero-variance fraction and collapse statistics from stored reward tensors, so the diagnostic is reproducible from evidence rather than from a live run; `p1_layer_profile.py` implements the white-box gradient probe; `parallel_sweep.py` and `campaign.py` drive sweeps (source: platform_tinker/reports/esa_phase1/Phase1_Project_Report_ZVF.tex).

The unrelated synthetic supervised fraud study is separated in Appendix F and is not evidence for the RL research questions. Beyond these modules, the `platform_local/unified/` package carries `canonical.py` for the canonical configuration and `peft_utils.py` for adapter handling, and the backends package implements one module per backend (`local.py`, `modal.py`, `colab.py`, `vast.py`, `gcp.py`, `hfspaces.py`) behind the common `base.py` interface (source: platform_local/unified/).

## 5.8 The Bridge and Sampler Path

Runners reach a Tinker-trained model through `zvf-program/flagship/modal_tinker_openai_bridge.py`, a Modal-deployed OpenAI-compatible bridge whose own header states that "the deployed bridge is infrastructure, not a benchmark result. Its default paid-inference budget is zero" (source: zvf-program/flagship/modal_tinker_openai_bridge.py). The bridge declares app name `campaign-serving-bridge`, model alias `campaign-actor` over model id `Qwen/Qwen3.6-35B-A3B`, and pins its sampler at [operational identifier withheld], with the Hugging Face side pinned by commit `withheld-adapter-revision`. Runtime limits are 16,384 maximum completion tokens against a 65,536-token model context, with an 8,192-token context prefix reserved; `DEFAULT_MAX_USD` is `Decimal("0.00")`, so every paid path must be opted into explicitly at launch. The pinned dependency set is `fastapi` 0.116.1, `huggingface-hub` 1.27.0, `tinker` 0.30.0, `transformers` 5.5.4, and `wandb` 0.21.0 (source: zvf-program/flagship/modal_tinker_openai_bridge.py).

The architectural point of the bridge is that it converts a Tinker sampler into an OpenAI-compatible endpoint. A harness written against the OpenAI chat-completions API — which most agentic benchmark harnesses are — can therefore be pointed at a Tinker-trained actor without modification, and the retained E4 diagnostic code addresses its `/v1/responses` form. Execution of the alleged later rerun is not authenticated by that code. The same pattern appears in the actor-side configuration of the E1 recovery wave, where the actor is addressed as an OpenAI-compatible chat-completions service at `http://127.0.0.1:18015/v1` (container port 8000) under model name `campaign-actor-bf16`, with `max_tokens` 8192, temperature 0, seed 809, top-p 0.95, and `chat_template_kwargs {"enable_thinking": false}` (source: zvf-program/e1_wave10/README.md). The bridge and the local actor endpoint are two deployments of the same interface contract, and keeping that contract stable across deployment modes is what allows one harness to serve both.

## 5.9 Recovery Re-implementations under `zvf-program/`

In the final phase of the project an execution-source loss — deletion of the historical temporary execution workspace directory — removed the finish-era recovery and build code, confined in scope to the E1 wave10 controller, the E9 restored dependencies, and the E6 validator, while the replacement-lane native runners survived under `zvf-program/flagship/` (source: outputs/E1_E14_FINAL_RESULTS_2026-09-19.md). Four such re-implementations are worth describing, because together they show what the evidence discipline looks like when it is expressed as code rather than as convention. The companion E2 `launch_gate.py` has a narrow check: it checks only that the amendment acceptance record and the surviving CORE-Bench harness entry points exist, which keeps the gate's claim small enough to be true (source: zvf-program/e2_core/launch_gate.py).

Read together, these four artefacts are the implementation answer to a question the results chapters raise: how a project maintains evidential integrity when its execution environment is partly lost and partly unreachable. The answer taken here is to re-derive the controllers from the sealed requests and the surviving test records, to keep every re-implementation offline-testable, and to make the no-retry, no-replay, hash-pinned, fail-closed properties explicit in code so that they can be demonstrated rather than asserted. The cost of that discipline is visible: four controllers, three of them complete and one a deliberate stub, produced no new benchmark numbers in this phase. That is the intended trade.

None of the four controllers ran the lanes in the end. On 27 September 2026 a single lead authorisation superseded the sealed-reservation and owner-binding gates they enforce, and each lane was run with a thin runner that calls the benchmark's native loop and grader directly. The runners live under `outputs/finish_pending_2026-09-27/<lane>/code/`, and each lane's `result.json` lists the bypass as a deviation (§8.4). These fail-closed properties therefore describe offline-tested replacement designs, not controls shown to have governed the measured replacement lanes. Authorisation to take a different path does not establish methodological equivalence. The campaign is reported as a pipeline demonstration with scoped receipts and unresolved training provenance (§4.5).
