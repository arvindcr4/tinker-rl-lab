# Appendix B. Reproducibility and Provenance

## B.1 What this appendix establishes

This appendix records three things that should not be confused with one another. The first is what a reviewer can independently re-run: a pinned container, a pinned dependency set, a headline training command, and the tolerance within which a rerun is expected to land. The second is what the repository verifies about itself without re-running any model: an audit suite driven by a single entry point, and a deterministic ledger check that recomputes the reported arithmetic directly from surviving evidence files. The third is provenance: which parts of this work were produced by the Semester 3 group, which by the individual contribution reported here, and what was lost along the way.

## B.3 The reviewer's entry point

`REPRODUCE.md` is the reviewer-facing document. The headline result is GRPO on Qwen3-8B over GSM8K for 30 steps at LoRA rank 32, group size 8 and seed 42, recorded as a peak per-step training accuracy (the binary reward) of 62.5 % with a last-10 average of 34.4 %; these summarise the training curve of the seed-42 run, not a held-out evaluation, and Table 1.1 lists them beside the other Qwen3-8B GSM8K figures they are sometimes confused with. Reviewer-side reruns are accepted within ±5 percentage points on the last-10 figure and ±10 points on peak, justified in the same document by the residual non-determinism discussed in §B.10. Per-seed reference values and W&B run identifiers are tabulated for seeds 42, 123, 456 and 789, with seed 1024 marked as a reviewer-only rerun; the canonical multi-seed set is `{42, 123, 456, 789, 1024, 2048, 4096, 8192, 16384, 32768}`. Five-seed aggregation runs through `utils/stats.py`, which now accepts `--bootstrap-samples` (default 10,000) and prints the mean, standard error and a percentile-bootstrap 95% interval; its `--format` flag now writes the requested CSV, LaTeX or both from the same computed summary, while `--rliable` explicitly rejects the unsupported CLI aggregation path because these files do not define a normalized task matrix. It reads a `results/<experiment>/seed_<N>/*.jsonl` layout that the trainer does not write, so a reviewer must write one metrics file per seed first, as `REPRODUCE.md` §3.4 states. `utils/verify_results.py` checks a rerun against `platform_hybrid/paper/expected_results.json` at those tolerances. It parses the per-seed `avg_last10` / `peak_reward` block that `grpo_cli` actually prints, and it exits non-zero when a value is outside tolerance or missing, when no result file matches an expected experiment, or (exit 2) when the expectations file or results directory is missing. Before the 3 October fix it parsed a line format the trainer never prints and exited 0 when nothing matched, so a failed rerun would have been reported as a pass; `tests/test_verify_results.py` now covers both formats and the failure cases. The October 4 correction preserves each result's seed and uses only an explicitly applicable reference. The shipped headline is scoped to seed 42; other seeds and historical unscoped references are reported as UNVERIFIED with a nonzero exit, rather than compared with the seed-42 value. Supported reference files can declare a per-seed mapping or an explicitly justified seed-independent reference. Missing or conflicting identities cannot pass a seed-specific comparison, and strict mode requires every declared seed reference to be represented. This changes validation applicability, not the historical measured values.

The cost is stated plainly: about five GPU-hours on a single A100-80GB for the headline run, against roughly 446 GPU-hours for a full paper reproduction. The 4 October code corrections address separate statistical boundary cases. Identical paired arms now return a two-sided p-value of one, and zero-standard-error equivalence tests reject effects on or outside the declared margin. These repairs change current helper behavior; they do not certify or rewrite historical experiment outputs. The aggregation flags and per-seed reference limitation in §B.3 remain present in the inspected code.

## B.5 The audit apparatus

The integrity suite is driven by a single entry point, `platform_local/run_all_audits.py`, which imports a shared result interface from `utils/audit_utils.py` and registers its audits as a tuple of name-and-function pairs. As it stands in this tree, that tuple contains **nine** audits: `claim_issues`, `sync_issues`, `anon_issues`, `strength_issues`, `package_issues`, `workflow_issues`, `export_guard_issues`, `caveat_issues` and `scientific_issues`. Each is implemented by a corresponding `platform_local/` module carrying a `__main__` block, so each can also run on its own; `tests/test_audit_runner.py` asserts that the registered modules and the `platform_local/*_audit.py` files are the same set.

Some repository documents give different counts, and the difference is historical. At the blind-review sweep the suite was thirteen audits, registered as a list of script filenames at the repository root and executed as subprocesses; the committed log of that run records `METRIC audits_total=13` with ten passing and three failing, and the same sweep states that all seventeen `*_audit.py` scripts then at the root were executed, with the suite covering thirteen of them. The registry now holds nine audits, all passing: a pruning commit removed obsolete audits, and a later restructuring replaced the subprocess runner with the in-process interface, so the seventeen-script description has narrowed by the same route. No script now prints a metric line directly; the line is constructed in one place, `AuditResult.metric_line()` in `utils/audit_utils.py`, and emitted by the nine audit modules plus the runner. A repository-wide scan finds several dozen files matching `*_audit.py`, but that population is not a suite: it includes unrelated analyses, test modules and a third-party file in the virtual environment.

The output contract is uniform. `AuditResult.metric_line()` emits `METRIC <name>=<issue_count>`, so every audit reports one machine-readable line whose right-hand side is the number of issues it found, and an audit passes exactly when that count is zero. `render_suite` prints each audit's metric line and issue codes, then three suite-level lines — `METRIC suite_issues`, `METRIC audits_total` and `METRIC audits_passing` — before either listing the failing audits by name or stating that all audits are passing. The entry point exits `0` when the suite passes and `1` otherwise, which makes it usable as a gate; the packaging step runs the suite before exporting and refuses to package if it fails. The runner's own test asserts this rendering against a synthetic two-audit suite, checking for `METRIC audits_total=2` and `METRIC suite_issues=1`.

## B.6 The deterministic ledger check

Where the suite above audits the submission package's internal consistency, a second instrument audits the campaign's reported figures. `outputs/verification/LEDGER_CODE_CHECK_2026-09-19.json`, under schema `ledger-code-check-v1`, records eleven checks of which eleven passed and none failed. They cover E1, E8 coverage, E9, E11 and E14 counts and hashes and the lost-source probes; they do not cover the E10 score, E8 accuracy, the E2, E4, E5 and E7 lanes or anything recorded after 19 September, and the E14 check confirmed the official scorer's 4,426-row denominator rather than the 4,428-row denominator this report uses. Each recomputes a claim from the underlying evidence rather than trusting a summary of it, and the four classes of check prove four different things.

| Class of check | Specific checks | What it proves |
|---|---|---|
| Exact divisions | E1 `2/731`; E11 `129/312`; E11 `67+62=129`; E14 `4426/4428` and accuracy `0.5131043831902395` (which is 2271/4426, the scorer's judged-row denominator; the reported headline counts the 2 unjudged rows as failures, 2271/4428 = 0.5129); E9 `40 of 75` | That each reported ratio is the quotient of the two integers the report claims, and that a partition sums to its whole |
| Receipt presence | E8 eight categories summing to 1967 with every `evaluated == expected_total`; E9 graded-row counts; the strict-completion set | That every claimed unit of coverage has a surviving graded row behind it, and that the set of strictly complete suites is exactly `[E8, E10, E11]` |
| Sealed-artefact hash equality | E1 v6 sealed request and fixture receipt | That the sealed request and the validation receipt are byte-identical to the artefacts recorded at sealing time |
| Lost-source absence probes | Source availability check | That four historical temporary execution workspace paths are genuinely absent, so a later re-creation cannot be mistaken for the lost original |

: The deterministic ledger check by class, listing each specific check and what it establishes.

The distinction matters under questioning. An exact division proves the arithmetic is not a rounding convenience or a transcription error; it cannot prove the underlying evidence is sound. A receipt-presence check proves coverage claims are backed by artefacts; it cannot prove those artefacts were produced correctly. A hash-equality check proves identity between two artefacts — here, between what was sealed and what was later validated — and is the strongest of the four because it does not depend on re-running anything. An absence probe proves a negative: it prevents a later reconstruction from being passed off as the original. Two instances show the classes in use. The historical E1 records describe matching request and validation bindings without establishing that execution occurred. Private request identifiers are withheld. The E9 records show 41 graded rows resolving to 40 unique competitions against a denominator of 75 in the streaming arm and exactly one valid grade in the merged-VLLM arm, which is the check that confirms the two serving arms were never pooled.

## B.7 The receipt model

A receipt in this campaign is a durable JSON artefact binding an outcome to the inputs that produced it, and the binding carries the evidential weight rather than the file's existence. The clearest statement of the principle is the receipt-bundle auditor's docstring, which records that the campaign and the receipt builders are kept deliberately separate from the auditor, and that the auditor "never imports a provider SDK, contacts a service, launches a job, or treats `status`/`online`/a URL/ID alone as provenance". The auditor reconstructs contract coverage, receipt predicates, canonical hash rules, budget caps and cross-artefact bindings, carrying its expectations as constants rather than reading them from what it checks — suite counts of 12 training, 14 primary-evaluation and 26 total — so a receipt set that quietly loses a suite fails the audit rather than redefining it.

Receipts bind four dimensions of a run: protocol, runtime, source and event order. The frozen-runtime record applies that discipline to the runtime dimension alone, binding five artefacts — protocol document, screening manifest, launch manifest, launch fingerprint and source binding — by SHA-256 and failing closed on any mismatch. The judgment layer for subjectively scored questions follows the same pattern: one durable receipt per judgment binds the state bytes, the question text and the raw answer, and battery execution is gated on a health check rather than the service's availability, so a degraded answer cannot be laundered into a valid one. Where a lane could not be scored, its terminal state is recorded in the ledger of record with a named reopen condition, so the absence of a result is itself receipted.

## B.10 Residual non-determinism and the limits of reproduction

Not everything here is reproducible in the strict sense, and the tolerances exist because of it. Three sources of residual non-determinism survive even with fixed seeds and deterministic cuDNN settings: remote LoRA training is not bit-deterministic across scheduler decisions, with runs replayed months apart drifting by two to four percentage points on GSM8K last-10, documented through three reruns of the same seed-123 configuration; some matmul operations on H100 and A100 hardware introduce non-determinism through CUDA and cuBLAS; and sampling at temperature 0.8 with top-p 0.95 executes in a remote virtual machine, so a fixed seed does not fix the sampled trajectory. The record states the consequence itself: run-to-run variance on this setup is of the same order as the effect reported in the paper's PPO-versus-GRPO comparison, which limits the historical saturated comparison. The newer unsaturated comparison (§6.5.5) is baseline-specific and test-sensitive, with paired-t p = 0.016 but exact sign-flip p = 0.0625; neither supports a general algorithm ranking.

Three limits remain. Lanes blocked on external access cannot be reproduced from this repository, because the blocking resource is not in it. The six lanes completed on 27 September can be rerun from the code in their lane directories under `outputs/finish_pending_2026-09-27/`, but only with cloud accounts, a served copy of the actor and, for E6, a judge account with credit; CORE-Bench's answer keys are deliberately kept out of the repository. The evidence-loss paths cannot be reproduced in their original form, only re-implemented against surviving fixtures, and that distinction should be preserved in any future citation. And figures originating at the Semester 3 boundary describe the tree at that tag, so reproducing them requires the worktree checkout rather than the current HEAD.

## B.12 Fresh-Sampling Diagnostic: Frozen Contract and Audit

The new evidence in §7.4 is run `V2 frozen-policy sampling study`, a sampling-only experiment with no weight updates. Its protocol, code, tests, expected cohort and parser were hash-bound before allocation or generation at 18:15:03 UTC on 2 October 2026. The freeze covers 26 files. Prompt ordering was deterministic and independent of scores, using seed 20261002; the V2 smoke and main cohorts are disjoint from each other and from the failed V1 smoke, and the request-seed namespace is disjoint from V1. The main cohort is 512 prompts and the independent smoke is 32 prompts, each with eight initial plus 24 fresh draws (sources: research/rescue_sampling_v2_protocol_2026_10_02.md; research/rescue_sampling_v2_freeze_2026_10_02.json; research/rescue_v2_expected_cohort_2026_10_02.json).

**Model and decoding.** Model and tokenizer are `Qwen/Qwen3-8B`, both at revision `b968826d9c46dd6066d109eabc6255188de91218`. The dataset is `openai/gsm8k`, configuration `main`, **train** split, revision `740312add88f781978c0658806c59bc2815b9866` (7,473 rows). The model used BF16 with thinking disabled, temperature 0.7, top-p 0.8, top-k 20, min-p 0, a 1,024-generated-token cap and 4,096-token context. Each request had n = 1 and its own seed; batching grouped four prompts. The recorded stack used vLLM 0.11.0, PyTorch 2.8.0, Transformers 4.57.1, eager execution and disabled prefix caching on one NVIDIA A100-SXM4-80GB. The supervised process completed in approximately 26.6 minutes, including loading and both cohorts. Hardware/kernel changes need not reproduce samples bit-for-bit (sources: withheld V2 generation source; withheld V2 generation source; withheld V2 generation source; withheld V2 generation source).

**Parser and review contract.** The V2 parser accepts specified explicit final-answer forms, normalises exact rational numbers and fails closed on malformed, conflicting or invalid claims; it does not search arbitrary prose for a number.
